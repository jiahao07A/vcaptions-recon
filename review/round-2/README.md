# 第二轮审查：验证修复是否真的成立

第一轮审查（`round-1/`）报了 87 项问题，随后四轮修复（`SUMMARY-round-1~4.md`）号称全部处理。本轮审查的目标**不是找新 bug，而是验证那些修复是否真的有效**。

## 核心问题：修复是否只是"看起来修好了"

前四轮暴露过一类反复出现的失效模式：

- `verify()` 曾经恒真（对任意切法都通过）
- `consistency.check` 的 i18n 断言循环论证（索引从审计读，再比两者一致）
- `bundles.load` 因 realm 污染，4 个 bundle 的回归完全不可见
- `browser-verify` 只探测 1/3 的入口页

这些都不是"功能没写"，而是**守卫看起来存在、实际拦不住**。因此本轮的判断标准是：

> 你能否构造一个场景，让这个"已修复"的守卫失效？

## 审查方法

对每一项声称的修复：

1. **读修复代码**，理解它声称保证什么
2. **构造反例** —— 想一个能让它失效的输入或操作序列
3. **实际执行** 反例，记录结果
4. 如果拦住了 → 这项修复成立，写进"已验证"
5. 如果没拦住 → 这是新发现，按严重度报告

**只读代码不算验证。** 必须跑命令。

## 分层

| 层 | 范围 | 重点验证 |
| --- | --- | --- |
| R1 构建守卫 | `build.mjs` 暂存/原子替换、语法校验、基线比对 | 能构造出「构建成功但 dist 有问题」吗 |
| R2 校验器与自检 | `check.mjs`、`consistency.check`、`validator.check` | 断言是否又有循环论证；覆盖面 |
| R3 测试隔离与真实性 | `bundles.load` 子进程、`chrome-env` 保真度、`smoke` 断言 | 破坏后能否捕获；模拟层是否偏离真实 Chrome |
| R4 编辑安全与 overlay | `reconstruct` 手改检测、`overlay.mjs` 边界、`adopt` | 能否绕过检测导致数据丢失 |

## 报告要求

沿用 `review/README.md` 的格式与严重级别，但每条发现的**现象**字段必须写清「哪个声称的修复失效了」。文件名写 `review/round-2/<层>.md`。

## 已知的剩余限制（不必重复报告）

- `browser-verify.mjs` 固定端口 9340
- 强杀进程时 Chrome profile 残留
- HTML `<title>` 保留 `__MSG_appName__`（刻意保留以维持字节一致性）
- `adopt --all` 中途失败留半成品
- `storage_keys` 对多层变量传递的键会漏
